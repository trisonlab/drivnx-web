# Full journey and project checks

## Outcome
The whole journey passes against the installed wheel, the CI configuration exists, every check also runs locally, and the performance and accessibility targets are measured.

## Acceptance checklist
- [x] AC-51 (US-09): Given a built wheel, when it is installed with `uv tool install`, then the `drivnx` command serves the bundled UI and API from one origin, and AC-01 passes against it.
- [x] AC-53 (US-09): Given the repo, then CI configuration runs pytest, Vitest, Playwright, secret scanning and dependency vulnerability checks. Each of those also runs locally with a documented command.
- [x] AC-54 (US-09): Given `testdata/`, then every file is synthetic and generated by a committed script or documented as hand-written.

## Expected evidence
Playwright journey against the wheel. Measured figures for the 1 GB CSV, an automated accessibility check, and a final spike 6 run. CI, macOS and Windows reported as NOT RUN until they can run.

## From the T01 review
- `uv build --wheel` succeeds with a missing or outdated UI bundle, and the wheel ships without it or with the old one. Reproduced in the T01 review. Provide one build command that builds the UI first and checks the result, and test it.
- The wheel declares `fastapi>=` and `uvicorn>=`, so `uv tool install` and the test install can pick versions newer than `uv.lock`. Choose how released versions are pinned (Section 7 of the direction doc), and make the test install match it.

## From the T02 review
- Some integration tests are POSIX-only: `os.killpg`, `send_signal(SIGINT)` and the shell-script browser stand-ins. Make them portable or mark them before running CI on Windows. On macOS, `webbrowser` finds browsers differently, so check that the tests still can't open a real one.

## Decisions in building this
- **`uv build --wheel` is the one build command.** A Hatch build hook (`hatch_build.py`) installs the UI from its frozen lockfile, removes any earlier build, builds it, and checks that `index.html` landed where the wheel picks it up. It skips editable installs, so `uv sync` doesn't need pnpm.
- **The wheel pins every runtime package, direct and indirect, to its `uv.lock` version,** using `uv export --locked`, so a lockfile behind `pyproject.toml` stops the build. DrivnX is an application in its own environment, so exact pins can't conflict with anything. A security fix in a dependency needs a new release. The ranges in `pyproject.toml` stay as they are. This holds for the built wheel only: `uv tool install .` reads those ranges and installs newer versions, so the README says to install the wheel. Pins fix versions, not file hashes, as wheel metadata can't carry hashes. Before this, the install under test held `sqlalchemy` 2.1.8 where `uv.lock` says 2.1.6.
- **The test install now uses `uv tool install`,** in private folders, so every test using `drivnx_executable` proves that route.
- **Secret scanning is `detect-secrets` from PyPI, run with `uvx`,** with `# pragma: allowlist secret` on a test's fake credentials and the two `.ai` files that can't be edited excluded. It's pinned as `detect-secrets@1.5.0`, as the scanner reads its own `==` form in the workflow as a secret being assigned. A baseline file was tried first, but it records line numbers, so adding a line above a recorded one failed the scan with no new secret. It looks at the current files only, not git history, and misses what it doesn't recognise, such as a bearer token in a shell script. `gitleaks` was the first choice as it scans history, but downloading and running its binary was refused by this session's permission system, so it was never tried. Scanning history is worth revisiting.
- **Tests that can't run elsewhere are marked, not ported.** `posix_only` covers signals, modes, links and shell-script browser stand-ins, and `linux_only` covers the `DISPLAY` rules and a browser command that fails, as `webbrowser` could then open a real browser on macOS or Windows. So the full journey test doesn't run on Windows yet. These marks are unproven until CI can run them.
- **The journey test records every browser request** and requires one origin. A `fetch` to another origin never leaves the page, as the app's CSP blocks it.
- **Accessibility:** axe-core 4.14.0 runs directly in the page for WCAG 2.2 A and AA tags, with no wrapper package, on setup and its error, the empty app, a failed connection, and a connected file with its preview. The tests don't cover the signed-out message, the two load failures, an unavailable source or a preview error, which the review found clean when it tried them by hand. No product change was needed. Keyboard use, a visible focus ring and reflow at 320 px have tests of their own. An automated check finds only part of what WCAG asks, so this doesn't prove conformance, and no screen reader has been tried.

## Measured
`tests/measure_large_csv.py`, through the real UI in Chromium, on 2026-11-05. A 1 GB synthetic file on this machine's NVMe disk, dropped from the page cache first. Budgets are 5 s for the metadata and 2 s for the first page.

| Encoding | Run | Rows | Metadata | First page after that | Connect to first page | Next three pages |
|---|---|---|---|---|---|---|
| UTF-8 | 1 | 26,120,000 | 3.86 s | 0.03 s | 3.89 s | 0.11, 0.15, 0.20 s |
| UTF-8 | 2 | 26,120,000 | 4.95 s | 0.23 s | 5.18 s | 0.16, 0.25, 0.25 s |
| Latin-1 | 1 | 26,570,000 | 4.39 s | 0.08 s | 4.47 s | 0.93, 0.89, 0.90 s |
| Latin-1 | 2 | 26,570,000 | 3.34 s | 0.05 s | 3.39 s | 0.36, 0.21, 0.33 s |

Every run is within budget, but only just for UTF-8's second, so a slower laptop will probably miss the 5 s. The budget is an assumption in the spec, and changing it needs a new revision. On tmpfs the same runs took 1.84 s and 1.35 s to the metadata. Two runs each, on one machine.

## Left as they are, from the review
- Linux CI may use the runner's own Chromium, as the tests pick `/usr/bin/chromium` when it exists, so `playwright install` may go unused there. Either way it's a real Chromium.
- `uvx` pins only the top package of its tools, so their indirect dependencies float. The jobs are read-only and hold no credentials.
